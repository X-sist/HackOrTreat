# T04 handoff: transmitter implementation

## Result

Implemented the transmitter sketch and pinned the build dependencies. The
current user-confirmed signal wiring is V1221 transmitter DATA to Uno D2 and
V1222 receiver DATA to Uno D3. The Tx sketch uses D2; receiver work remains
T05. This is user-reported wiring, not a manufacturer-verified module pinout.

The sketch validates bounded `SEND` commands, builds the shared v1 binary
envelope and CRC-16/CCITT-FALSE, emits the defined Tx JSON-line events, and
sends full NEC symbols at the shared start-to-start schedule. It uses the
generated header through a repository-root compiler include path. No protocol
contract or generated file was changed.

## Pins and references

- Arduino CLI 1.5.1, official release; Windows x64 archive SHA-256 is recorded
  in `dependencies.json`.
- Arduino AVR core 1.8.8, official `ArduinoCore-avr` release.
- IRremote 4.7.1, official library release. Its tagged NEC implementation
  supports 16-bit addresses and `sendNEC(address, command, 0)` emits a full
  frame without repeats.
- Official Uno R3 documentation confirms ATmega328P board family; it does not
  document the V1221/V1222 modules.
- Public lookup did not locate primary manufacturer documentation for the
  exact V1221/V1222 identifiers. Power/ground pins, module polarity, drive
  limits and carrier compatibility are still unknown and must not be guessed.

## Verification

- Installed CLI 1.5.1, AVR core 1.8.8 and IRremote 4.7.1 into ignored
  `firmware/.local/`.
- `arduino-cli compile --fqbn arduino:avr:uno --warnings all` with the repo-root
  include path: PASS.
- Compile report: 5,014 bytes flash (15%); 784 bytes static RAM (38%), leaving
  1,264 bytes for stack/runtime.
- User clarified the physical roles: Rx Uno is COM4, Tx Uno is COM5. Both
  sketches were uploaded to their matching boards.
- User-reported current module spacing is under 0.5 m. The later consecutive
  maximum-payload run passed at the aligned bench setup; the exact measured
  distance during each individual transfer was not recorded.
- Serial boot events `hello` and Tx `ready`: PASS on the correctly identified
  ports.
- Live short packet `SEND\t12345678\t000C\t4869`: Rx COM4 emitted the exact
  `message` event with payload `4869`; Tx COM5 emitted `accepted`, `sent`, and
  `ready`.
- Initial 48-byte payload attempts were intermittent (2/3 passed); a later
  uninterrupted run of eight 48-byte payloads all emitted exact `message`
  events on Rx COM4. This confirms maximum-size physical transfer is possible
  and passed eight consecutive tries, but not a statistically established
  reliability rate.
- Rx's raw diagnostic decoded the continuous maximum-packet symbol sequence.
  IRremote classifies the closely-spaced full frames after the first as NEC2;
  Rx now accepts those full NEC2 frames and continues to reject short NEC repeat
  frames.
- Idle silence produced no unexpected events during a 15-second observation.
- After a clear-path short-message control passed, the user blocked the IR path
  for about three seconds during a maximum-size production transmission. Tx
  emitted `accepted`/`sent`; Rx emitted no message for that packet. After the
  path was clear, a short production recovery packet arrived with the exact
  payload. This is bench evidence at the user-reported close spacing, not a
  range or reliability claim.
- Receiver partial-packet timeout, CRC rejection, index-gap detection, and
  packet-timeout behavior were exercised with controlled diagnostic IR sends;
  a valid production packet was delivered after those injections.
- Module pin documentation/electrical limits, longer optical range,
  ambient-light behavior, and measured worst-case timing remain unverified.
- `python tools/check_repo.py` and `python tools/validate_protocol_vectors.py`:
  PASS. `node tools/check_js_contract.mjs`: PASS.
- Firmware status remains implemented, not complete: real-world transfer and
  physical recovery are confirmed at the close bench setup. Longer range,
  ambient-light behavior, measured timing, and primary module electrical
  documentation remain outstanding.

## Status

T04 is implemented: the Tx has been compiled, uploaded, and verified in real
two-board transfers, including eight consecutive maximum-size packets at the
user-reported close bench setup (<0.5 m), plus a user-operated physical
obstruction followed by successful recovery. It remains implemented rather
than complete because longer optical range, ambient-light behavior, measured
timing, and primary module electrical documentation are not verified. The COM
port mapping and current close spacing are user-reported; module
pinout/electrical limits are not manufacturer-verified.
